- The plan contract has one definition: `plugins/dev-flow/scripts/plan-schema.sh`. `plan-check.sh` sources it, `plan-check.sh --template` prints the plan skeleton from it, and `tests/plan-check.sh` checks that the filled-in template passes and that this file, `agents/spec-architect.md` and `README.md` repeat its value sets. Change a value there first, then the files the test names.
- Header (every line before the first `## `): `Status:` DRAFT|APPROVED|IN_PROGRESS|DONE, `Approved:` yes|no, `Spec:` a repo-relative path that exists; an optional `Plan review: <model> <effort>` line (model sonnet|opus, effort high|xhigh|max: never below sonnet high, because it reviews the architect's own plan); an optional `Review: <model> <effort>` line (model haiku|sonnet|opus, effort low|medium|high|xhigh|max); optional `Override:` lines.
- `## Tasks` holds `### Task N: <title>`, numbered 1..n with no gaps. Each task's first line is `Task status:` NOT_STARTED|IN_PROGRESS|DONE (`PLAN_TASK_STATUS`; a bad or missing value is `task-status`; tasks at IN_PROGRESS or DONE skip the existence checks), then the labels `Objective:`, `Files:`, `Test first:`, `Test command:` (one backticked command) and `Done when:` (`- ` items; ``- run `<command>` and expect <result>`` items are verify commands), plus optional `Change:`, `Depends on:` (earlier tasks or `none`) `Risk:` low|medium|high, `Model:` haiku|sonnet|opus and `Effort:` low|medium|high|xhigh|max. A bad `Model:`, `Effort:`, `Plan review:` or `Review:` value is `route-value`. These lines set the Agent `model` and `effort` parameters for the matching dispatch; a missing line passes nothing, so the job runs on the session's current model and effort (`implementer`, `plan-reviewer` and `reviewer` use `model: inherit`).
- A title may start with one tag: `### Task N: [<tag>] <title>`, tag in backend|frontend|qa|devops|docs (`PLAN_TAGS`); build sends untagged tasks to `implementer`, tagged ones to their agent. Unknown tags, implementation tasks after a `[qa]` task (only `[docs]` and `Manual:` may follow), and a tagged `Manual:` task are `task-tag`.
- `Files:` entries are `- <verb> <repo-relative path>` with the verb create|modify|delete|rename|test, written `- rename <old> -> <new>` for a rename; no absolute paths and no `..`; at most 6 entries per task.
- Plan writes have owners. The implementer moves its own task's `Task status:` forward only: IN_PROGRESS before it writes any file, DONE when every verify passes, adds the paths it touched to its own `Files:` block and appends its own `- Task N: <text>` lines to `## Deviations`, one line per deviation. The build writes only the `Status:` and `Approved:` header lines, `Manual:` task status and Deviations entries and, if an implementer replied BLOCKED without writing it, the BLOCKED line. `- Task N: BLOCKED: <reason>` under `## Deviations` is an unresolved escalation (`PLAN_BLOCKED`): the user clears it by rewriting it as `- Task N: RESOLVED: <decision>`. plan-check prints `open=` and `blocked=` lines for it, and `plugins/dev-flow/scripts/plan-edit-check.sh` enforces the write boundary.
- Placeholders TBD and TODO and the phrases in `PLAN_PLACEHOLDER_PHRASES` are errors outside backticks and fences; put them in backticks when a plan has to name them. The `## Deviations` section is exempt.
- A code fence must be closed: an unclosed one hides the rest of the plan from the validator (`fence-unclosed`, not overridable). `verify-toolchain` and `unlisted-path` are heuristics: write verify commands with the tool as the first word (`bash x`, not `(cd sub && bash x)` or `FOO='a b' cmd`), and use `Override:` only for a real false positive.
- `Override: <code|all> task <N>: <reason>` and `Override: <code|all> plan: <reason>` are written only by the user or at the user's explicit request, never to make a plan pass. Every run prints them as `overridden=` lines and the build passes them to the reviewer.
- Structural checks only: never add a rule that scores or judges plan quality; that is the plan-reviewer's job.
- A new finding code needs an entry in `PLAN_CODES`, a defect fixture in `tests/plan-check.sh` and a row in the README code table.
- Keep `plan-check.sh` working on bash 3.2 and BWK awk: no associative arrays or `mapfile` in bash; no `asort`, `IGNORECASE`, `\b`, regex intervals or `match()` capture arrays in awk; pass schema values to awk through `ENVIRON`, not `-v`.
