---
description: Implement an approved plan task by task with cheaper Sonnet subagents, then review with Opus and verify.
argument-hint: <slug of the plan in .claude/plans>
model: sonnet
---

Implement the approved plan `.claude/plans/$ARGUMENTS.md` (spec: `.claude/specs/$ARGUMENTS.md`).

You are the orchestrator, running on the cheaper model. Keep your own context small: delegate the coding.

0. Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/plan-check.sh" .claude/plans/$ARGUMENTS.md` from the repository root and keep its full output for step 6. If it exits 2, report its `error=` and `summary=` lines and stop. If it exits 1, show me every `error=` line verbatim and its `summary=`, say that no task will be dispatched, and stop: I fix the plan, or, for a finding I judge a false positive, I add `Override: <code> task <N>: <reason>` (or `Override: <code> plan: <reason>`) to the plan header and run the build again. Never add or edit an `Override:` line yourself, and never edit the plan to make it pass. If it exits 0 and the output has any `blocked=` line, show those lines and stop: I resolve each by rewriting it as `- Task N: RESOLVED: <decision>`. If it exits 0 otherwise, show me each `warning=` and `overridden=` line (or say there are none), then, because this build is my approval, set the plan header's `Approved:` line to `Approved: yes` and its `Status:` line to `Status: IN_PROGRESS`. In worktree mode, make these two edits on the worktree copy of the plan once step 2 has created it (that copy is the one named in `Plan:`), and leave the original plan in the main checkout unchanged. Because the worktree may start from the default branch, whose files can differ, then re-run `plan-check.sh` on that worktree copy before any `implementer` is dispatched and handle the result exactly as above (exit 2: report and stop; exit 1: print every `error=` line with the override hint and stop; exit 0: print the `warning=` and `overridden=` lines). In branch mode make the edits now. This step is the gate in hookless mode too: never skip it.
1. Read the plan and the spec. If the spec has an unresolved "Open questions" section (older specs), stop and tell me. `assumed` rows are not blockers, and neither are numbered questions with a `default:` under the spec's table: their defaults stand. Step 0 already refused a missing plan and any `blocking` row.
2. If any task's checkbox is already `- [x]`, this is a resume: skip the questions below and continue in the current checkout and branch, but first run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/default-branch.sh"` from the repository root; if it prints `on_default=yes`, do not continue: tell me and ask, since I may switch back to the feature branch. A worktree build resumes from a session started inside its worktree. Otherwise choose where the work happens and which branch it starts from, before any `implementer` runs. First name the branch: pick `<type>` from the spec's goal (`fix` if it corrects a bug, `refactor` if it restructures code without changing behaviour, `chore` if it is maintenance that changes no product behaviour such as dependencies, build, CI, tooling, docs or a version bump, otherwise `feature`), then run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/branch-name.sh" <type> <slug>` from the repository root. Its `branch=` value is `<branch>` below; it already includes the project prefix from `.claude/branch-prefix` when the repo has one. If it exits 1, report its `error=` and `summary=` lines and stop.
   - Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/default-branch.sh"` from the repository root. Offer the base choice only if it exits 0, prints `on_default=no`, and `git status --porcelain -- . ':!.claude/plans' ':!.claude/specs' ':!.claude/worktrees'` is empty. Otherwise start from the current branch: if the script exited 1, give its `summary=` line; if the tree has uncommitted changes, say in one line that starting from the default branch is not offered because switching base could mix or lose those changes.
   - Offer **Worktree** only if `git rev-parse --git-dir` and `git rev-parse --git-common-dir`, both run from the repository root (`git rev-parse --show-toplevel`), print the same path and `EnterWorktree` is among your tools. Otherwise use **Branch** and say why in one line (this session is already in a linked worktree, or `EnterWorktree` is unavailable).
   - Ask me once, with one `AskUserQuestion` call holding the questions that apply: header `Git workflow`, question "Where should this build happen?", options **Branch (default)**: "Work in this checkout. <branch> is created unless you are on a non-default branch and start from it, in which case the work stays on that branch." and **Worktree**: "Create a separate checkout in .claude/worktrees/<slug> on <branch>; this checkout stays untouched."; and header `Start from`, question "Which branch should the work start from?", options **Current branch (default)**: "Start from <current branch, or HEAD if detached> as it is now." and **Default branch**: "Start from <default= value>, the repository's default branch." Leave out any question my approval to build already answers, and do not call `AskUserQuestion` if none is left. If `AskUserQuestion` is unavailable, use the defaults. Any answer that is not a clear choice of **Worktree** means **Branch**, and any answer that is not a clear choice of **Default branch** means **Current branch**.
   - **Branch**: if the tree has unrelated uncommitted changes, stop and ask (`.claude/plans`, `.claude/specs` and `.claude/worktrees` do not count). Never work on the default branch. With **Current branch**: if `default-branch.sh` exited 1 (no default branch found), you are on the default branch, or you are on a detached HEAD, run `git switch -c <branch>`; on any other branch, stay on it. With **Default branch**: run `git switch --no-track -c <branch> <ref>`, where `<ref>` is the script's `ref=` value.
   - **Worktree**: run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/worktree.sh" <slug> <branch> <start>` from the repository root, where `<start>` is `HEAD` for **Current branch** or the `ref=` value for **Default branch**. If it exits 1, report its `error=` and `summary=` lines and stop; for `error=copy-failed` the worktree and branch already exist, so also tell me the cleanup commands in its `summary=` and do not run them yourself. Otherwise call `EnterWorktree` with its `path=` value. From then on all commands, every `implementer` and the reviewer work in that worktree, and its `.claude/specs/` and `.claude/plans/` hold copies of the spec and plan. If it printed `ignored=no`, tell me to add `.claude/worktrees/` to `.gitignore`. If it printed `dirty=yes`, tell me that uncommitted changes in the original checkout are not in the worktree. Do not use any other worktree procedure or skill.
3. Dispatch tasks one at a time, never in parallel, because each `implementer` writes the plan. The order is that of the `open=` lines in the latest plan-check output, lowest first; never dispatch a ticked task. Invoke the `implementer` subagent with only that task, the spec sections it references, and the spec's "Assumptions and open questions" section. Before each dispatch, run `cp <plan> <plan>.before`, using the `Plan:` path. In worktree mode, also give each `implementer` the worktree path and tell it that every path in its task means the same repo-relative path inside that worktree. Start every `implementer` prompt with the line `Plan: <path>` and, on the second line, `Task: <N>`, where `<path>` is `.claude/plans/<slug>.md` in branch mode and the absolute path of the plan copy inside the worktree in worktree mode; where hooks run, the dev-flow implementer gate denies a call without it. If the gate denies an `implementer` call, stop and show me its message verbatim; do not retry with another agent or work around it. A task whose title starts with `Manual:` needs me: do not dispatch it; show me its `Change:` and `Done when:`, wait for my reply, then, only if I report it done, tick its checkbox yourself, append my report as one `- Task N: <text>` line under `## Deviations` and continue with the next `open=` task; if I say it cannot be done, leave it unticked, append `- Task N: BLOCKED: <text>` and stop.
4. The `implementer`, not you, ticks its task, extends its Files block and appends its Deviations lines; never tick or write Deviations for a dispatched task. After each `implementer` reply:
   1. Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/plan-edit-check.sh" <plan>.before <plan> <N>`. On exit 1 or 2, show its `error=` and `summary=` lines and stop.
   2. Re-run plan-check on the plan.
   3. If the reply reports every verify passing, confirm that no `open=N:` line remains. Otherwise stop and report that the implementer did not tick Task N.
   4. If the reply is `BLOCKED`, or does not report every verify passing, and plan-check prints no `blocked=N ` line, append `- Task N: BLOCKED: <the reason in one line>` under `## Deviations`. Then stop and report. Do not re-dispatch, do not tick, and do not edit the plan to get past a gate. Do not improvise design changes.
5. When all tasks are done, run the `verify-done` skill (tests, lint, behaviour check).
6. Invoke the `reviewer` subagent (Opus) on the full diff. It has no shell, so collect its inputs yourself and paste them into the prompt:
   - `base=$(git merge-base HEAD "$(git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null || echo main)")`
   - the diff: `git diff "$base"` (committed and uncommitted work), plus each new file from `git ls-files --others --exclude-standard -- . ':!.claude/plans' ':!.claude/specs' ':!.claude/worktrees'` shown with `git diff --no-index /dev/null <file>`. New files under `.claude/plans/` and `.claude/specs/` are left out of that list, so if the plan's deliverable lives there, pass those files to the reviewer explicitly. If the result is too large to paste, pass `git diff --stat "$base"` and the list of changed and new files instead, and say the reviewer must Read them.
   - the log: `git log --oneline "$base"..HEAD`
   - the output and exit code of `bash .claude/test-cmd`, or "no .claude/test-cmd" if it does not exist
   - the output of `bash "${CLAUDE_PLUGIN_ROOT}/scripts/plan-check.sh" .claude/plans/$ARGUMENTS.md`, re-run just before invoking the reviewer (not only step 0's, so an override I added mid-build is shown), including every `overridden=` and `warning=` line, and the plan's `## Deviations` section (or "no deviations")
   - the output and exit code of `bash "${CLAUDE_PLUGIN_ROOT}/scripts/plan-scope.sh" <plan> "$base"`, re-run before each review
   - the spec and plan paths (in worktree mode, the copies inside the worktree).
   If it returns `CHANGES REQUIRED`, send blocker and major findings back to `implementer` as new tasks, each dispatch starting with the same `Plan: <path>` first line as in step 3 (the gate denies it otherwise) and a `Task: <N>` second line, where N is the task whose Files block lists the finding's path, or the highest-numbered task if none does; take the same snapshot and run the same step-4 checks. Do not send `scope-drift` findings to the implementer; they are mine to decide (record or revert). Then re-review once, collecting fresh inputs.
7. Re-run plan-check. Set the plan's `Status:` line to `Status: DONE` only if it prints no `open=` and no `blocked=` line (in worktree mode, on the worktree copy; the original in the main checkout stays unchanged); otherwise leave `IN_PROGRESS` and list those lines. Delete `<plan>.before`. Finish with: what was built, files changed, evidence of verification, remaining review findings, scope drift (every `drift=` path and the reviewer's scope-drift findings), every plan-check override and deviation (from the step-6 plan-check output), and anything not verified. Do not merge or push. Always give the branch name; in worktree mode also give the worktree path, say this session is still inside the worktree, and that after merging it is removed with `git worktree remove <path>`. Do not remove it yourself.
