Plan this work: $ARGUMENTS

Use the `spec-architect` subagent to do the investigation, the clarification check and the writing, so planning runs on the strong model even if this session was started on a cheaper one. It cannot talk to me mid-run; you relay its questions.

Steps:

1. Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/plan-check.sh" --template` and `echo "${CLAUDE_PLUGIN_ROOT}/scripts/plan-check.sh"`. Delegate to `spec-architect` with the full request, the template output as the plan skeleton, and the plan-check command `bash <that path>`. On a re-run, also pass its earlier reply and my answers. Ask it to run its clarification check, then produce `.claude/specs/<slug>.md` and `.claude/plans/<slug>.md`.
2. If its reply starts with `BLOCKING`, no files were written. Send me its numbered questions verbatim, in one message, under `**Questions for you**`, and stop. Do not add, drop or reword questions, and do not ask any of your own. When I reply, go back to step 1.
3. Read both files it wrote. Check that the spec ends with an "Assumptions and open questions" section with one row for each of the seven categories, that the plan header has a `Plan review:` and a `Review:` line, and that every task not titled `Manual:` has a `Model:` and an `Effort:` line; if not, send it back once with specifics. Then run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/plan-check.sh" .claude/plans/<slug>.md`. If it exits 2, report its `error=` and `summary=` lines and stop. If it prints any `error=` or `warning=` line, send those lines verbatim to `spec-architect`, with its earlier reply, to revise the plan, then run plan-check again: at most 3 revision attempts in total, then go on to step 4 whatever the result. Never add an `Override:` line yourself, and never edit the plan yourself to make it pass.
4. **Plan review.** Run it only if the last plan-check run exited 0, otherwise skip to step 5 and record `plan review not run: plan-check fails`. Get the absolute repo root with `git rev-parse --show-toplevel`, falling back to `pwd`, and check whether `.codegraph/` exists. Then, from this session and never from inside `spec-architect`, delegate to the `plan-reviewer` subagent with the spec and plan paths (paths, not file contents), that plan-check output, the repo root and whether `.codegraph/` exists. Before the first `plan-reviewer` dispatch, read the plan header's `Plan review: <model> <effort>` line once. On every `plan-reviewer` dispatch in this round, set the Agent tool's `model` and `effort` parameters to those values, even if a later revision changes the line; this step is the explicit instruction to set them. If the line is missing, omit both, so the plan reviewer runs on this session's current model and effort. If the Agent tool has no `effort` parameter, omit it and say so once. If the first non-blank line of its reply is `PASS`, go to step 5. If it is `REVISE`, send its numbered findings verbatim to `spec-architect`, with its earlier reply, to revise the spec and plan, telling it to fix each finding or, for one it judges wrong, leave the plan unchanged and write one line `Disputed N: <reason>`; if that reply starts with `BLOCKING`, handle it as in step 2. Then run plan-check again; if it prints any `error=` or `warning=` line, send those lines to `spec-architect` once and run plan-check again, and if it still exits 1 stop reviewing, go to step 5 with `plan review stopped: plan-check fails after revision` and the last `REVISE` findings. Otherwise delegate to `plan-reviewer` again with the same inputs plus its previous findings and the `Disputed` lines. Allow at most 2 revisions from review findings: if the review after the second revision still replies `REVISE`, do not revise again but go to step 5 and escalate its findings. On any other reply, show it and go to step 5 with `plan review: no verdict`.
5. Summarise for me: the design in five lines or fewer, the task count, the routing read from the plan (one line `Plan review: <model> <effort>` with the values the review used, one line `Task N: <model> <effort>` per task, `Task N: Manual` for a `Manual:` task, `session` for a missing value, then one line `Review: <model> <effort>`, then the sentence "Edit these lines in the plan to change which model and effort build and review each part."), the plan-check result: `ok`, or every remaining `error=` line with a note that `/dev-flow:build` will refuse the plan until they are fixed or I override a false positive with an `Override: <code> task <N>: <reason>` header line; then the plan-review result, which is `PASS after <n> review(s)`, `plan review not run: plan-check fails`, `plan review stopped: plan-check fails after revision` followed by the last `REVISE` findings verbatim, `plan review: no verdict`, or, after the cap, its remaining findings verbatim under `**Plan review: unresolved**` followed by the sentence "The plan reviewer still reports these after 2 revisions. Answer or dispute them, edit the plan, or reply `ok build` to build it as it is."; then every `Disputed` line, every `warning=` and `overridden=` line, each `assumed` row in one line, then its numbered questions under `**Questions for you**`, each with its default. If it replied `Fully specified: no questions.`, write that line instead of the questions. If there are questions, add: "Answer any of them to override its default and I will revise the spec and plan." Then end with exactly this, filling in the slug:

   > Review `.claude/plans/<slug>.md`. Reply **`ok build`** to start the build phase right here, or run `/dev-flow:build <slug>` yourself instead — that switches the orchestration to Sonnet for this phase; replying `ok build` keeps it on the current model (each `implementer` and the `reviewer` still run on the model and effort the plan names either way, so most of the cost is the same).
